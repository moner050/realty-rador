# 필터 변경 시 0.001초(1ms) 초고속 반응을 위한 4대 최적화 전략 보고서

## 1. 개요 및 도전 과제
- 사용자가 지역(서울/경기/인천), 거래유형(매매/전세/월세), 가격대, 면적 등의 필터를 빈번하게 변경할 때, 매번 DB를 새로 조회하면 수백 밀리초(ms)의 지연이 발생합니다.
- 필터 변경 시에도 **인메모리(1ms) 속도**를 유지하기 위한 4대 핵심 아키텍처 전략을 제시합니다.

---

## 2. 4대 초고속 필터링 전략

### 1) 마우스 호버 & 백그라운드 프리페치 (Pre-fetching)
- **작동 원리**: 사용자가 지역 선택 칩("서울특별시", "경기도" 등)이나 필터 드롭다운에 마우스 커서를 올리거나(Hover), 고급필터를 펼치는(Accordion Open) 순간, 사용자가 선택할 가능성이 높은 인근 조건의 상위 1,000개 청크를 **백그라운드에서 Redis로 미리 비동기 호출**하여 적재합니다.
- **효과**: 사용자가 실제로 클릭했을 때는 이미 Redis에 데이터가 100% 준비되어 있어 **0.001초(1ms)** 만에 화면이 전환됩니다.

### 2) 다빈도 인기 필터 조합 사전 웜업 (Pre-warming)
- **작동 원리**: 서버 시작 시 및 매일 오전 06시 전체 크롤링 완료 직후, 사용자 이용률의 90% 이상을 차지하는 **상위 10대 필터 조합**의 1,000개 청크를 Redis에 미리 자동 캐싱해둡니다:
  - `[서울 + 매매]`, `[서울 + 전세]`, `[경기 + 매매]`, `[인천 + 매매]`
  - `[서울 + 디딤돌/버팀목 대출 적격]`, `[최신 3일 이내 매물]`
- **효과**: 일반적인 필터 변경 요청의 90% 이상이 DB 조회를 거치지 않고 Redis 인메모리에서 즉시 0ms 처리됩니다.

### 3) 프론트엔드 디바운스 (Debounce 300ms) + HTMX 부분 갱신
- **작동 원리**: 가격 및 면적 슬라이더/인풋 조절 시 키보드 입력마다 쿼리가 날아가는 것을 방지하기 위해 300ms 입력 대기(Debounce)를 적용합니다.
- **효과**: 전체 페이지 재로딩 없이 `#listings-container` 영역만 HTMX로 스와프(Swap)하여 UI 깜빡임(Flicker) 없이 매끄럽게 갱신됩니다.

### 4) Redis Hash / Set 기반 인메모리 복합 인덱싱 (In-Memory Faceted Search)
- **작동 원리**: 매물 수집 시 Redis 내부 집합(Set)에 `region:서울`, `tx:SALE`, `price_range:3_5억` 등으로 매물 ID 목록을 파티셔닝해둡니다.
- **효과**: 복합 필터 변경 시 Redis `SINTER` 교집합 연산으로 ID를 0.1ms 만에 뽑아내어 초고속 서빙합니다.

---

## 3. 요약 및 적용 권장
- **1단계 (즉시 적용 완료)**: 1,000개 청크 캐싱 및 1~50페이지 1ms 슬라이스 반환.
- **2단계 (추천)**: 다빈도 필터 조합 사전 웜업 및 호버 프리페치 적용 시 필터를 막 변경해도 0.001초 만에 갱신됩니다.
