# 필터 변경 시 갱신 속도 지연 원인 분석 및 성능 최적화 계획서

## 1. 지연 발생 근본 원인 분석 (Bottleneck Analysis)

### 1) 필터 변경으로 인한 Redis Cache Miss 발생
- **현상**: 서버 시작 시 웜업(Pre-warming) 해둔 9가지 대표 필터 조합(6억 이하, 서울/경기/인천 등) 이외에 사용자가 가격/면적/단지명/거래유형 등의 필터를 하나라도 변경하면 `base_cache_hash`가 바뀌어 **Redis Cache Miss**가 발생합니다.
- **영향**: 캐시 미스 시 매번 MySQL 데이터베이스에 직접 Heavy SQL 쿼리가 구동됩니다.

### 2) 30여 개 키워드 와일드카드 (`LIKE '%...%'`) 조건에 의한 DB Full Table Scan
- **현상**: 단기임대/노이즈 매물 원천 차단을 위해 `ListingSearchService`에서 `description_raw`, `address_raw`, `complex_name_raw` 컬럼에 대해 30여 개가 넘는 `%키워드%` 조건을 `OR` / `AND` 절로 매 쿼리마다 검사합니다.
- **영향**: MySQL DB에서 `%`가 앞단에 포함된 `LIKE` 조건은 인덱스를 전혀 사용할 수 없으므로, 14만~50만 건 전체 매물 테이블 레코드를 매번 전체 스캔(Full Table Scan)하여 심각한 쿼리 지연(1~3초 이상)이 일어납니다.

### 3) 과도한 1,000개 청크 단위 DB 조인 쿼리 및 전체 Count 서브쿼리
- **현상**: 사용자가 요청한 페이지는 20개 임에도 불구하고, 캐시 미스 발생 시 Redis 캐시 적재를 위해 1,000개 매물과 연관된 `ApartmentComplex`, `CrawlSource` 테이블 전체 조인 데이터를 DB에서 한 번에 쿼리하고 객체로 직렬화합니다.

## 2. 성능 최적화 개선 전략 (Proposed Solutions)

### 1) 단기임대 / 노이즈 플래그 DB 인덱스 컬럼화 (`is_short_term` / `is_noise`)
- 매번 쿼리 시 30여 개의 `LIKE '%단기%'` 조건을 태우는 대신, 매물 크롤링/정규화/저장 시점에 단기임대 여부를 판단하여 `is_short_term` (Boolean 인덱스 적용 컬럼)으로 미리 DB에 보관합니다.
- 쿼리 조건을 `WHERE is_short_term = FALSE` 1개 조건으로 줄여 인덱스를 타게 함으로써 쿼리 속도를 1ms 대로 단축시킵니다.

### 2) Cache Miss 시 온디맨드 쿼리 분리 (필요 페이지 우선 즉시 반환)
- 캐시 미스가 발생한 실시간 필터 변경 요청 시에는 1,000개를 한 번에 조회하지 않고, 요청한 20개(또는 100개)만 우선 초고속 조회하여 사용자 화면에 10ms 이내에 즉시 응답하도록 개편합니다.
