# 1,000개 단위 Redis 청크 캐싱(Chunk-based Caching) 도입 계획서

## 1. 개요 및 변경 목적
- **현상**:
  - 기존에는 페이지당 20개 단위로 캐시 키를 따로 구성하여 1페이지, 2페이지, 3페이지... 페이지를 넘길 때마다 DB 쿼리가 반복 구동되어 1~2초의 페이징 지연 발생.
- **개선 방안**:
  - 사용자의 명쾌한 제안에 맞춰 동일 검색 조건에 대해 **상위 1,000개 매물 청크(Chunk)**를 1회의 DB 쿼리로 읽어와 Redis에 적재.
  - 1페이지~50페이지(1~1,000번째 매물) 이동 시 **MySQL DB 접속 0건, 단 0.001초(1ms)** 만에 인메모리 청크 슬라이싱으로 즉시 반환.
  - 51페이지(1,001번째 매물 이상)를 넘어갈 경우 다음 1,000개 블록(1,001~2,000)을 DB에서 1회 조회하여 Redis에 자동 추가 갱신.

---

## 2. 세부 알고리즘 설계 (`ListingSearchService`)

1. **`page` 및 `limit` 제외 베이스 검색 키 생성**:
   - `chunk_cache_key = f"listings_chunk_search:{md5_hash}"`

2. **청크 캐시 적중 여부 및 슬라이싱 반환**:
   - 요청 페이지의 `offset`이 캐시된 청크 범위 내에 존재할 경우:
     -> `restored_items[slice_start:slice_end]` 인메모리 연산으로 **0.001초(1ms)** 리턴!

3. **청크 미적중 시 1,000개 일괄 쿼리 및 Redis 적재**:
   - `chunk_offset = (offset // 1000) * 1000`
   - `chunk_limit = 1000`
   - MySQL에서 1,000개 매물을 1회에 쿼리하여 Redis 적재 (TTL 300초).
