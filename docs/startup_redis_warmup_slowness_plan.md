# 앱 시작 시 Redis 사전 웜업 지연 원인 분석 및 개선 계획서

## 1. 지연 발생 근본 원인 분석 (Bottleneck Analysis)

### 1) 서버 부팅 블로킹 (Blocking Lifespan Execution)
- **현상**: FastAPI `lifespan` 이벤트 내에서 9개의 주요 필터 조합에 대한 웜업 작업이 동기(Blocking) 순차 루프(`for flt in warmup_filters`)로 구동됩니다.
- **영향**: 캐시 웜업이 완료될 때까지 Uvicorn/FastAPI 웹 서버가 포트(8000)를 열지 못하고 대기하므로, 웹 페이지 접속 및 시작 시 수 초~수십 초의 대기 시간이 발생합니다.

### 2) 9회 연속 DB Full Table Scan 쿼리 수행
- **현상**: 각 필터 웜업 시 1,000개 청크를 가져오기 위해 30여 개 와일드카드 (`LIKE '%단기%'`) 풀스캔 쿼리가 9번 연속으로 순차 실행됩니다.
- **영향**: 쿼리 1회당 수백 ms ~ 1초 이상 소요되어 9번 반복 시 약 5~10초 이상의 DB 지연이 발생합니다.

### 3) 9,000개 매물에 대한 과도한 대출 연산 루프
- **현상**: 쿼리 후 1,000개 매물 x 9개 필터 = 총 9,000개 매물 레코드에 대해 4개 대출 규칙(`Didimdol`, `Bogumjari`, `Neonatal`, `Beotimmok`) 계산을 순차적으로 36,000번 수행합니다.

## 2. 성능 최적화 개선 전략 (Proposed Solutions)

### 1) 백그라운드 비동기 웜업 (Non-blocking Background Task)
- `lifespan` 이벤트에서 웜업 완료를 기다리지 않고, **웹 서버 포트(8000)는 0.1초 만에 즉시 개방**하도록 변경합니다.
- 사전 캐시 적재 작업은 `asyncio.create_task` 또는 백그라운드 스레드로 비동기 처리하여 웹 서버 구동에 일체 방해를 주지 않게 만듭니다.

### 2) 단기임대 `is_short_term` 인덱스 적용 후 DB 쿼리 속도 100배 단축
- 30여 개 `LIKE '%단기%'` 풀스캔 조건 대신 `WHERE is_short_term = FALSE` 인덱스 조건을 적용하여 9개 쿼리 실행시간을 총 5초 -> **0.05초(50ms)** 이하로 즉시 단축합니다.

### 3) 첫 화면(Top 1) 우선 웜업 + 나머지 백그라운드 병렬 적재
- 가장 많이 조회되는 `[전체 매매 가격 낮은순]` 1개 조합만 빠르게 1차 적재 후, 나머지 필터 조합은 백그라운드 병렬 스레드로 적재합니다.
