# 지도 계층형 집계 설계

## 목표

조건에 맞는 매물을 지도 축척에 맞게 적은 수의 원형으로 먼저 보여주고, 충분히 확대했을 때만 단지별 매물 수를 표시한다. 지도 이동 중에는 기존 결과를 유지하고 작은 헤더 진행 상태만 보여 준다.

## 축척 단계

| 지도 줌 | 응답 모드 | 지도 표현 | 클릭 동작 |
| --- | --- | --- | --- |
| 0~8 | `sido` | 시·도별 원형, 축약 매물 수 | 해당 시·도 실제 좌표 범위로 확대 |
| 9~12 | `sigungu` | 시군구별 원형, 시군구명과 매물 수 | 해당 시군구 실제 좌표 범위로 확대 |
| 13~14 | `clusters` | 가까운 단지의 작은 원형 묶음 | 묶음 범위로 확대 |
| 15 이상 | `markers` | 단지별 원형 마커와 조건 충족 매물 수 | 기존 단지 매물 모달 열기 |

시·도와 시군구 원은 매물 수(`listing_count`)를 표시한다. 숫자는 `950건`, `1.2천 건`, `1.3만 건` 형식으로 축약한다. 단지 마커는 개별 매물 대신 단지 하나당 하나로 표시해 같은 단지의 다수 매물이 화면을 덮지 않게 한다.

## 데이터와 성능

- 모든 단계는 현재 필터와 지도 경계, 검증된 좌표 조건을 적용한다.
- 일반 필터는 후보 매물 CTE를 단지별로 집계한 뒤, 낮은 줌에서는 `ComplexCurrent.sido_code` 또는 `sigungu_code`로 SQL `GROUP BY` 한다. 낮은 줌 응답은 전체 단지 좌표를 파이썬으로 전송·클러스터링하지 않는다.
- 정책 대출 필터처럼 파이썬 스트림 경로가 필요한 경우에도 같은 4단계 응답 모드를 유지하되, 이미 필요한 단지 요약과 좌표만 메모리에서 집계한다.
- 각 원에는 평균 좌표와 실제 구성 단지의 최소·최대 경계를 넣어 클릭 확대가 해당 그룹을 정확히 포함한다.
- 스키마·마이그레이션·외부 수집·지오코딩 호출은 추가하지 않는다. 추가 DB 인덱스는 운영 데이터의 `EXPLAIN ANALYZE` 근거 없이는 도입하지 않는다.

## 지도 갱신과 목록

- 지도는 서울·경기·인천이 보이는 중심 `(37.55, 126.9)`, 줌 `8`에서 시작한다.
- 첫 로드에서는 API를 요청하지 않는다. 사용자가 이동·확대를 끝낸 뒤 1.5초가 지나면 현재 축척의 지도 집계를 요청한다.
- 새 조작은 이전 타이머와 진행 중인 지도·카드 요청을 취소한다. 최신 뷰포트 키와 요청 토큰만 화면을 갱신한다.
- 전체 지도를 흐리는 로딩 레이어는 사용하지 않는다. 지도 헤더와 카드 제목의 작은 진행 표시만 변경하고, 이전 마커·카드 목록은 새 응답이 도착할 때까지 유지한다.
- 지도 아래 카드 목록은 줌 11 이상에서 현재 경계 기준으로 갱신한다. 낮은 줌의 시·도/시군구 집계 단계에서는 카드 요청을 만들지 않는다.

## 인터페이스 계약과 검증

- 지도 JSON `mode`는 `sido`, `sigungu`, `clusters`, `markers` 중 하나다.
- 기존 `markers`, `clusters`, 단지·매물 수 필드는 유지한다. 시·도/시군구 원은 기존 클러스터 구조에 선택적 `label`을 더해 전달한다.
- 테스트는 각 줌 단계의 그룹·숫자·범위, 경계·필터 적용, 높은 줌 단지 모달, 낮은 줌 카드 요청 생략, 1.5초 지연 및 최신 요청만 반영하는 동작을 보장한다.
- 브라우저에서는 초기 줌 8, 세 단계 원형 표현, 원 클릭 확대, 단지 모달, 로딩 레이어 부재를 확인한다.

## 실행 환경 주의

이 변경은 `codex/map-exploration-interactions` 작업트리에서 구현한다. 현재 사용자가 보고 있는 `localhost:8000`이 주 작업트리의 기존 서버라면 이 변경이 보이지 않는다. 검증 후에는 이 브랜치를 통합하거나, 이 작업트리에서 서버를 실행해야 한다.
